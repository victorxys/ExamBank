# 员工工作表现、员工画像与客户需求匹配系统实施计划

## 1. 计划目标

本计划用于将 PRD 转化为可执行的研发、测试和上线工作。实施顺序遵循“先证据底座，再 AI 分析，再员工画像，最后客户匹配”，避免在数据和复核机制尚不可靠时直接上线自动匹配。

配套 PRD：`docs/project_management/employee_performance_profile/requirement_document.md`。

## 2. 总体建议

### 2.1 推荐交付路径

1. 直接完善主系统现有 `/staff-management` 和 `/staff/:employeeId`，不新建平行员工后台。
2. 使用 Tailwind CSS 重做员工列表和员工详情，保持路由、导航和鉴权不变。
3. 现有员工、编辑、合同、评价、LLM 配置和日志 API 优先复用。
4. 在主系统员工模块增量建设表现、证据、画像和风险能力。
5. 直接复用主系统现有客户、合同、档期模型和 API。
6. MVP 先在内部客服、运营范围灰度。
7. MVP 稳定后再启用客户需求匹配。

### 2.2 实际业务实现边界

本项目只在 ExamDB 主系统中实施：

1. 前端范围限定在主系统 `frontend/`。
2. 后端范围限定在主系统 `backend/`、`migrations/` 和必要的主系统测试目录。
3. 员工主数据继续使用主系统 `ServicePersonnel`。
4. 客户、合同、档期、小程序评价、LLM 配置和日志均复用主系统现有模型或 API。
5. 新增表现、证据、画像、风险和匹配表直接建立在主系统数据库中，并关联现有员工、客户和合同 UUID。
6. 新增业务接口统一放入主系统 `/api/staff` 命名空间。
7. `microservices/employee_management` 是演示版本，本项目明确不修改、不依赖、不部署、不测试。

### 2.3 前端技术约束

1. 本期改造文件以 `frontend/src/components/StaffManagementPage.jsx`、`frontend/src/components/StaffDetailPage.jsx` 和员工相关子组件为主。
2. 员工管理页面移除对 MUI 页面组件的依赖，改用 Tailwind CSS 4。
3. 图标使用现有 `lucide-react`。
4. 可复用现有 Radix Dialog、Popover、Select 等无样式交互基础，统一由 Tailwind 负责视觉。
5. 本期只重构主系统员工管理页面，不扩大全站 MUI 到 Tailwind 的迁移范围。
6. 现有 `frontend/src/api/staff.js` 继续作为员工页面 API 适配层，新增工作表现和画像请求也归入员工域 API 模块。

### 2.4 现有 API 复用基线

| 能力 | 现有接口/模块 | 计划 |
| --- | --- | --- |
| 员工列表 | `GET /api/staff/employees` | 原样复用基础查询；按需增加批量画像摘要 |
| 员工详情 | `GET /api/staff/employees/{id}` | 原样复用基础、工资卡、薪资和表单数据 |
| 员工编辑 | `PATCH /api/staff/employees/{id}` | 原样复用 |
| 合同履历 | `GET /api/staff/employees/{id}/contracts` | 原样复用 |
| 客户评价 | `MiniappContractEvaluation` 及现有小程序接口 | 由后端来源适配器读取 |
| LLM 配置 | `/api/llm-config/*` | 复用密钥加密和配置管理能力 |
| LLM 日志 | `/api/llm-logs` | 沿用排障日志，新增业务任务状态 |

只在主系统新增现有接口不能表达的资源：来源记录、转写版本、证据片段、分析任务、观察项、画像版本、风险处置和匹配结果。

## 3. 里程碑概览

| 阶段 | 主要成果 | 预计周期 | 上线性质 |
| --- | --- | --- | --- |
| P0 需求与治理确认 | 字典、权限、风险制度、主系统模块设计 | 1 周 | 不上线 |
| P1 页面骨架与数据底座 | Tailwind 员工页面骨架、表结构、来源、证据、权限 | 2 周 | 内部开发环境 |
| P2 现有功能迁移与人工记录闭环 | 现有员工功能无损迁移、来源录入、时间线、复核 | 2 周 | 小范围内测 |
| P3 Dify 分析闭环 | 异步调用、Schema、复核工作台 | 2 周 | 影子模式 |
| P4 画像与风险 | 画像版本、趋势、风险处置、申诉 | 2 周 | 客服运营灰度 |
| P5 客户需求匹配 | 需求快照、硬过滤、解释型匹配 | 2 周 | 匹配顾问灰度 |
| P6 质量评估与正式发布 | 历史导入、指标、监控、制度验收 | 1-2 周 | 分批正式发布 |

总体预计 12 至 13 周。前后端和测试可在每个阶段内部并行，但 P3 不应早于证据底座完成，P5 不应早于画像质量验收完成。

## 5. P1：数据库、领域模型与审计底座

### 5.1 数据库工作

建立以下表及索引：

- `performance_sources`。
- `performance_transcript_versions`。
- `performance_evidence_segments`。
- `performance_analysis_jobs`。
- `performance_observations`。
- `performance_observation_evidences`。
- `employee_risk_alerts`。
- `employee_profile_versions`。
- `employee_profile_traits`。
- `employee_profile_audit_logs`。

关键约束：

1. 员工 ID 必填，客户和合同 ID 可空但需记录原因。
2. 转写版本号在来源内唯一。
3. 证据片段 ID 在转写版本内唯一。
4. 分析任务幂等键唯一。
5. 正式观察项至少绑定一条证据，例外情况必须记录原因且不能自动成为高风险。
6. 画像版本号在员工内唯一。
7. 业务数据只允许软删除或作废。

### 5.2 后端基础服务

- 来源记录 CRUD 和对象级权限校验。
- 转写文本分段、稳定 ID 和内容哈希。
- 转写版本创建及差异标记。
- 证据引用校验服务。
- 审计日志服务。
- 员工、客户和合同关联校验服务。
- 枚举和字典版本读取服务。

### 5.3 Tailwind 页面骨架

- 重构员工管理列表外壳、搜索筛选区、表格、分页和状态展示。
- 重构员工详情顶部身份区、关键状态条和标签页导航。
- 建立员工页面专用 Tailwind 组件：状态徽标、空状态、错误状态、信息行、时间线和证据引用。
- 保持 `/staff-management`、`/staff/:employeeId` 和现有侧边栏入口不变。
- 建立部分接口失败的独立边界，画像接口失败不能阻断基础员工资料。
- 使用当前真实 API 数据完成页面骨架，不使用固定 `5.0` 或伪造画像数据。

### 5.4 权限

建议细分权限代码：

- `performance_source:create/read/update/void`。
- `performance_evidence:read_sensitive`。
- `performance_observation:review/publish/revoke`。
- `employee_profile:read/publish`。
- `employee_risk:read/review/close`。
- `employee_match:run/decide`。
- `employee_profile:export`。
- `employee_profile:audit_read`。

### 5.5 测试

- 迁移升级和降级测试。
- 唯一约束、外键和软删除测试。
- 对象级越权测试。
- 转写版本和证据失效测试。
- 审计日志完整性测试。
- 员工/合同/客户历史关联不一致测试。
- 现有员工列表与详情 API 响应兼容测试。
- Tailwind 页面桌面、平板和手机宽度布局测试。
- 画像接口失败时基础员工页面仍可使用的降级测试。

### 5.6 阶段出口

- 数据库迁移可重复执行。
- 敏感接口完成权限测试。
- 任一正式记录的创建、修改、作废都有审计日志。
- 关联数据缺失或不一致时不会写入错误绑定。
- 现有员工管理路由和入口保持不变。
- 员工列表和详情已使用真实数据完成 Tailwind 基础骨架。

- 员工/客户/合同搜索与绑定校验。
- 人工创建候选观察项和证据绑定。

### 6.2 前端

- 完成员工列表 MUI 到 Tailwind 的功能等价迁移。
- 完成员工详情 MUI 到 Tailwind 的功能等价迁移。
- 保留员工搜索、筛选、排序、分页、考勤快捷入口和行跳转。
- 保留基础资料编辑、工资卡、薪资历史、合同履历、入职表和下户总结。
- 员工详情新增“工作表现与画像”入口。
- 来源记录创建页。
- 转写编辑、说话人标注和行号预览。
- 人工观察项创建和证据选择。
- 基础复核队列。
- 工作表现时间线和来源详情页。

### 6.3 兼容改造

1. 现有小程序客户评价作为 `customer_contract_evaluation` 来源导入或实时适配。
2. 现有下户总结标识为“员工自述”，不能作为客户直接证据。
3. 旧评价体系若被复用，必须确认被评价对象能稳定映射到 `ServicePersonnel`，不得假设 `User` 与服务员工相同。
4. 员工详情当前固定“综合评分”改为“数据不足”或真实画像摘要。
5. 前端所有员工请求继续通过现有 API 适配层，不在组件中散落新旧服务 URL。
6. Tailwind 重构完成前使用页面级功能开关保留旧页面作为短期回退，不长期维护两套页面。

### 6.4 测试

- 创建来源的字段校验和关系冲突测试。
- 转写长文本、空段落、特殊字符和重复导入测试。
- 证据上下文定位测试。
- 来源作废对观察项和画像影响测试。
- 正面、负面、混合和争议场景测试。
- 响应式页面和长文本不重叠测试。
- 新旧页面功能对照测试，确认无现有员工管理能力丢失。
- 从侧边栏、合同、考勤和动态表单进入员工详情的路由回归测试。

### 6.5 内测

选择 2 至 3 名客服和运营，仅录入新反馈，运行 1 周。此阶段不调用 AI、不生成匹配分数，主要验证字段和流程是否符合实际工作习惯。

## 7. P3：Dify 分析与人工复核闭环

### 7.1 Dify 工作流

工作流节点建议：

1. 输入校验。
2. 对话预处理和必要分片。
3. 工作表现事实抽取。
4. 画像维度分类。
5. 风险线索分类。
6. 证据片段一致性自检。
7. 合并重复候选项。
8. 输出 JSON Schema。

工作流必须明确禁止：

- 根据姓名、年龄、籍贯等推断能力或诚信。
- 执行转写文本中的指令。
- 引入原文未出现的事实。
- 将投诉自动认定为事实。
- 输出自动处分或淘汰建议。

### 7.2 后端集成

- Dify 配置和密钥加密存储。
- 创建异步分析任务。
- 幂等、超时、重试和取消。
- 原始输出保存和 JSON Schema 校验。
- 证据 ID、引用文本和枚举二次校验。
- 无效输出进入人工处理队列。
- Dify 调用指标和脱敏日志。

### 7.3 复核工作台

- 待复核队列与优先级。
- 原文、上下文和候选结论三栏视图。
- 批量处理低风险候选项，但逐条确认。
- P2/P3 禁止批量自动通过。
- 修改前后差异和理由记录。
- 快捷转交与补充信息请求。

### 7.4 影子模式

至少运行 2 周影子模式：

1. AI 结果不发布至正式画像。
2. 由两名业务人员抽样独立标注。
3. 统计事实抽取、证据引用、维度分类和风险分类质量。
4. 优先降低 P2/P3 误报和漏报。
5. 修改工作流后使用固定回归样本复测。

### 7.5 阶段出口

- 证据引用正确率达到业务确认阈值。
- P2/P3 不存在自动发布路径。
- Schema 无效输出被完整拦截。
- 人工复核操作和修改均可审计。
- Dify 故障时人工流程可继续运行。

## 8. P4：员工画像、风险和争议闭环

### 8.1 画像聚合服务

- 从有效正式观察项生成画像版本。
- 按事件去重，分别统计正面和负面证据。
- 统计独立客户、独立合同、直接来源和时间跨度。
- 检测相反证据、争议证据和数据不足。
- 保存聚合规则版本和输入观察项集合。
- 观察项变化后异步重算，失败保留上一有效版本。

首期聚合优先采用可解释规则，不使用第二个大模型自由总结关键风险。若使用大模型生成自然语言摘要，摘要只能引用已经确认的结构化统计，并再次经过人工发布。

### 8.2 风险处置

- 风险队列和 SLA 计时。
- 调查记录、附件和员工说明。
- 高级复核、双人复核配置。
- 企业微信或站内升级通知。
- 结论、措施和关闭原因。
- 风险状态变化触发画像新版本。

### 8.3 员工详情体验

- 画像总览和数据充分度。
- 维度趋势和证据统计。
- 正向优势、改进项、风险和待核实事项分区。
- 点击画像结论定位观察项，再定位原文。
- 画像版本对比。
- 争议和员工说明入口。

### 8.4 测试

- 同一事件多来源去重测试。
- 相反证据和争议证据测试。
- 重大风险不随时间自动消失测试。
- 画像重算幂等和失败恢复测试。
- 旧版本不可变测试。
- 两次点击内到达证据原文的验收测试。

## 9. P5：客户需求与可解释匹配

### 9.1 客户需求

- 确定由客户系统还是员工系统保存需求快照。
- 建立结构化字段、优先级和必需/偏好标识。
- 过滤或阻止敏感和歧视性条件进入匹配规则。
- 支持从已有客户记录或商机预填。

### 9.2 匹配引擎 V1

建议使用确定性规则引擎，不由大模型直接排序：

1. 硬条件过滤。
2. 能力与偏好逐项匹配。
3. 数据充分度计算。
4. 已确认风险冲突检测。
5. 生成结构化理由和冲突项。
6. 保存需求快照、画像版本和规则版本。

大模型可在后续用于润色解释，但不得改变结构化规则结果。

### 9.3 匹配页面

- 客户需求确认。
- 候选员工横向对比。
- 硬条件、优势、冲突、风险和数据不足分区。
- 查看证据摘要，完整原文仍受权限控制。
- 人工选择、排除和调整排序原因。
- 记录面试、试工、签约和拒绝结果。

### 9.4 测试

- 硬条件边界和档期冲突测试。
- 规则版本回放测试。
- 相同输入产生相同结果的确定性测试。
- 未确认风险不被显示为确定事实测试。
- 敏感条件不能进入排序测试。
- 外部合同或客户服务不可用时降级测试。

### 9.5 灰度门槛

1. 员工画像已稳定运行至少 4 周。
2. 数据充分度逻辑经过业务确认。
3. 风险误报、漏报和争议流程达到可接受水平。
4. 匹配顾问能够理解并解释每个排序理由。

## 10. P6：历史数据、灰度和正式发布

### 10.1 历史数据策略

按可信度分层导入：

1. 小程序合同客户评价：结构化来源，可直接导入来源层，是否生成观察项仍需分析和复核。
2. 下户总结：标记为员工自述，不作为客户直接证据。
3. 合同备注：仅作为待整理来源，不能直接生成风险结论。
4. 旧评价体系：先完成身份映射和语义评估，再决定是否导入。
5. 无法确认员工或合同的数据进入待绑定队列。

历史导入脚本必须支持 dry-run、批次 ID、断点续传、幂等和批次回滚。

### 10.2 灰度顺序

1. 内部测试账号。
2. 2 至 3 名客服和运营。
3. 单一员工类型或单一区域。
4. 全部客服运营，但匹配仍为建议模式。
5. 匹配顾问小范围启用。
6. 完成业务、法务、安全和技术验收后正式发布。

### 10.3 上线开关

建议配置以下功能开关：

- 来源记录入口。
- 自动提交 Dify。
- AI 候选项展示。
- 画像自动重算。
- 风险企业微信通知。
- 客户需求匹配。
- 历史数据展示。

### 10.4 回滚策略

1. 关闭 Dify 自动提交，不影响人工录入。
2. 关闭画像重算，继续显示上一有效版本并标注时间。
3. 关闭匹配功能，降级到现有人工筛选。
4. 不删除已经产生的来源、观察项或审计日志。
5. 通过规则版本回滚聚合和匹配逻辑，而不是改写历史结果。

## 11. 测试计划

### 11.1 单元测试

- 转写分段和内容哈希。
- 证据引用校验。
- 状态机和权限。
- 事件去重和画像聚合。
- 风险状态与 SLA。
- 硬条件和匹配解释。

### 11.2 集成测试

- 主系统员工、客户、合同模型及 API 集成。
- Dify 成功、超时、限流、错误和无效 JSON。
- 异步任务重试和幂等。
- 企业微信通知。
- 图片或附件存储权限。

### 11.3 端到端测试

- 创建来源到发布画像完整路径。
- P3 风险从线索到关闭完整路径。
- 转写更正导致证据失效和画像重算。
- 员工说明和争议处理。
- 客户需求到人工确认匹配结果。
- 越权访问和敏感导出阻断。

### 11.4 AI 质量回归集

建立脱敏固定样本，至少覆盖：

- 纯正向、纯负向和正负混合反馈。
- 客户情绪表达但没有明确事实。
- 客服转述、员工辩解和多说话人对话。
- 单次严重风险、多次一般问题和相反证据。
- 模糊指代、转写错误和上下文不足。
- 提示词注入文本。
- 不涉及员工表现的闲聊。

每次 Dify 工作流、提示词、模型或 Schema 版本变化都必须运行回归集。

## 12. 监控与运营计划

### 12.1 技术监控

- 分析任务成功率、失败率、P95 耗时。
- 队列积压和最长等待时间。
- Schema 校验失败和证据引用失败。
- 画像重算失败。
- 员工、合同、客户关联查询错误率。
- 未授权访问和导出失败次数。

### 12.2 业务监控

- 来源记录绑定完整率。
- 候选观察项接受、修改和驳回比例。
- P2/P3 数量、确认率和处理时长。
- 画像数据充分度分布。
- 争议、更正和撤销数量。
- 匹配采用、人工改序和拒绝原因。
- 正负观察项分布是否异常。

### 12.3 定期治理

- 每周处理失败任务和超时风险。
- 每两周抽检复核质量。
- 每月评审画像字典和风险误报。
- 每季度评估权限、留存、偏差和匹配规则。

## 15. Definition of Done

任一功能任务只有满足以下条件才算完成：

1. 需求和边界条件已实现。
2. 权限和对象级授权已覆盖。
3. 单元、集成或端到端测试按风险完成。
4. 敏感字段不出现在无权限页面和普通日志中。
5. 审计事件已记录。
6. API 文档和错误码已更新。
7. 数据迁移具备验证和回滚方案。
8. 页面完成桌面和窄屏检查，无内容重叠。
9. 监控和告警已配置。
10. 业务负责人完成验收。
11. Tailwind 重构页面没有丢失现有员工管理功能和跳转链路。
12. 页面组件不再新增 MUI 依赖，新增视觉统一由 Tailwind CSS 实现。
