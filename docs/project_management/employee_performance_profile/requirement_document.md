## 1. 背景

员工在上户服务期间，客户会通过电话、微信或其他沟通渠道向客服、运营反馈员工的实际工作表现。这些反馈既包括正面认可，也包括问题、投诉、风险线索和需要持续观察的事项。

当前反馈主要分散在聊天记录、电话录音转写、客服个人记录、合同备注、客户评价和下户总结中，存在以下问题：

1. 反馈没有统一绑定员工、客户和合同，难以形成完整履历。
2. 记录方式不统一，评价员工全靠记忆，不全面，很难根据客户的沟通结果做全面的评估与分析。
3. 结论与原始对话脱离，无法快速核验“为什么得到这个评价”。
4. 单次反馈与长期特征混在一起，容易形成不准确、不可纠正的员工标签。
5. 客户需求匹配主要依赖人工经验，无法系统利用历史服务表现。
6. 诚信、态度、安全等高影响风险缺少统一分级、复核和处置流程。

本项目需要建立从“原始对话证据”到“客观工作表现”，再到“版本化员工画像”和“可解释客户匹配”的完整链路。

### 1.1 已确认的产品入口和改造边界

本项目不是新建一套孤立的“员工画像后台”，而是完善现有员工管理能力：

1. 继续使用主系统现有员工管理入口 `/staff-management`。
2. 继续使用主系统现有员工详情入口 `/staff/:employeeId`。
3. 在现有员工列表和员工详情中加入工作表现、员工画像、风险和匹配信息。
4. 现有页面使用 MUI 实现，本期将员工管理列表和员工详情页面局部重构为 Tailwind CSS。
5. 保持现有路由、导航入口、鉴权方式和员工 ID 不变，避免产生两套入口和用户迁移成本。
6. 后端优先沿用现有员工、合同、客户评价、LLM 配置和调用日志 API，只为缺失的表现、证据、画像、风险与匹配能力新增接口。
7. `microservices/employee_management` 下的独立员工管理前后端属于演示版本，明确不在本项目范围内，不作为功能、数据或接口依赖。

## 2. 产品原则

1. **事实与结论分离**：原始转写、证据片段、业务观察和员工画像分别存储。
2. **全链路可追溯**：任何正式画像结论都必须能定位到来源记录和具体原文。
3. **AI 只生成候选结果**：Dify 和大模型不得绕过人工复核直接发布正式画像。
4. **正负反馈同等记录**：不能只积累投诉，也不能用总体好评掩盖明确风险。
5. **一次反馈不等于稳定人格特征**：画像必须表达证据数量、时间、来源独立性和不确定性。
6. **风险结论慎重**：未经核实的内容只能标记为风险线索或争议事项，不能表述为确定违法或失信。
7. **匹配可解释、可干预**：系统提供推荐理由和冲突提示，最终决定由授权业务人员作出。
8. **允许申诉和纠正**：错误绑定、错误转写、错误结论和后续澄清都必须可更正并留痕。
9. **最小化敏感信息**：仅保存完成业务目的所需的客户和员工信息，并执行访问、导出和留存控制。
10. **完善现有入口**：员工画像必须融入现有员工管理工作流，不建设重复页面或平行后台。
11. **增量复用后端**：能由现有 API 稳定提供的数据不得重复创建另一套接口和数据源。

## 3. 项目目标

### 3.1 业务目标

1. 统一沉淀员工上户期间的真实客户反馈。
2. 将非结构化转写转化为可复核、可统计的工作表现观察项。
3. 建立随时间演进、证据透明的员工画像。
4. 对诚信、态度、安全、财物、隐私等重点风险及时预警。
5. 在客户需求匹配时综合硬条件、员工能力、历史表现和风险冲突。
6. 降低客服和运营依赖个人记忆进行匹配的风险。

### 3.2 产品成功指标

首期灰度运行 8 周后评估：

| 指标 | 目标 |
| --- | --- |
| 新增反馈绑定员工、客户、合同的完整率 | 不低于 95% |
| 正式观察项具有有效证据片段的比例 | 100% |
| AI 候选结果完成人工复核的比例 | 不低于 95% |
| 正式画像结论可定位原文的比例 | 100% |
| 高风险线索在规定时限内被复核的比例 | 不低于 95% |
| AI 候选观察项人工接受率 | 灰度期不低于 70%，仅作为模型改进指标 |
| 匹配结果包含可读理由和冲突说明的比例 | 100% |
| 画像相关更正和争议处理有完整审计记录的比例 | 100% |

### 3.3 非目标

首期不包含：

1. 录音自动转写，首期只接收人工导出的文字版或已有转写结果。
2. 使用大模型自动作出录用、解聘、停单、处分或永久禁用决定。
3. 面向客户公开完整内部员工风险画像。
4. 基于年龄、籍贯、民族、婚育、宗教、疾病等敏感或受保护属性进行负面判断。
5. 在没有证据片段的情况下由 AI 自由生成员工评价。
6. 一期即训练自有模型；优先使用 Dify 工作流编排和受控结构化输出。

## 4. 用户与角色

| 角色 | 主要职责 | 核心权限 |
| --- | --- | --- |
| 客服 | 接收客户反馈、导入转写、补充上下文 | 创建来源记录、查看本人负责记录、提交分析 |
| 运营 | 管理上户过程、复核一般表现 | 创建和编辑记录、复核 P0/P1、查看员工画像 |
| 高级复核人/风控 | 处理重大风险和争议 | 复核 P2/P3、发布或撤销风险、查看完整证据 |
| 匹配顾问 | 根据客户需求选择员工 | 查看可用于匹配的画像摘要、发起匹配、反馈结果 |
| 业务负责人 | 制定分类、风险和处置规则 | 查看全局数据、审批策略、处理申诉 |
| 系统管理员 | 配置 Dify、权限和字典 | 系统配置，不默认拥有业务证据查看权 |
| 审计人员 | 核查敏感操作 | 只读查看审计日志及授权范围内证据 |
| 员工 | 提交说明或申诉 | 在授权流程中查看相关结论摘要、提交异议和补充材料 |

权限必须区分“查看画像摘要”“查看证据原文”“查看客户身份”“复核风险”“导出数据”等能力，不得只使用单一管理员角色覆盖全部权限。

## 5. 核心概念

| 名称 | 定义 |
| --- | --- |
| 来源记录 | 一次客户沟通、评价、投诉、回访或其他反馈的原始记录 |
| 转写版本 | 某来源记录的文字内容版本，修改后生成新版本而非覆盖 |
| 证据片段 | 转写中的连续原文行，包含说话人、行号和可选时间戳 |
| 候选观察项 | AI 或人工提出、尚未复核的单条工作表现判断 |
| 正式观察项 | 经授权人员确认、可参与画像聚合的客观记录 |
| 风险线索 | 可能涉及重大体验、安全、财物或法律风险的待调查信息 |
| 员工画像 | 根据有效观察项生成的版本化能力、行为和风险摘要 |
| 客户需求快照 | 发起匹配时客户需求的不可变版本，用于复盘匹配结果 |
| 匹配结果 | 员工与需求之间的硬条件、适配项、冲突项及解释 |

## 6. 端到端业务流程

### 6.1 工作表现沉淀流程

1. 客服或运营创建来源记录。
2. 选择员工，并尽可能绑定客户和合同。
3. 粘贴或上传文字转写，系统按段落生成行号。
4. 操作人确认说话人和基本上下文，提交 AI 分析。
5. 系统异步调用 Dify，并验证结构化返回结果。
6. 复核人逐条查看候选观察项及上下文。
7. 复核人确认、修改、驳回、合并或标记争议。
8. 正式观察项进入员工时间线，触发画像重算。
9. 若存在 P2/P3 线索，进入独立风险复核和处置流程。
10. 新画像发布为一个新版本，旧版本永久保留。

### 6.2 客户需求匹配流程

1. 匹配顾问创建或选择客户需求。
2. 系统保存需求快照，并从合同系统查询档期和合同硬条件。
3. 系统先执行硬条件过滤，再计算能力和偏好适配度。
4. 系统检查已确认风险与客户重点需求之间的冲突。
5. 返回候选员工、推荐理由、冲突项、数据不足和证据摘要。
6. 匹配顾问人工选择、排除或调整排序，并填写原因。
7. 后续记录面试、试工、签约、拒绝或上户结果，用于评估规则，但不得自动强化有偏见的结论。

列表建议字段：

| 字段 | 数据来源 | 说明 |

#### 7.0.2 员工详情

保留现有路由 `/staff/:employeeId`，使用 Tailwind CSS 重新制作员工详情。页面信息架构为：

1. 顶部员工身份区：姓名、照片、岗位、在职状态、当前服务状态、返回列表和编辑资料。
2. 关键状态条：档案完整度、画像数据充分度、最近反馈、待复核数量、风险状态。
3. `概览`：基础与入职信息、工资卡摘要、当前合同、最新薪资、最近工作表现。
4. `工作表现`：来源时间线、正负反馈、服务阶段、客户/合同上下文和创建入口。
5. `员工画像`：优势、改进项、画像维度、证据充分度、趋势和画像版本。
6. `风险与争议`：风险线索、调查状态、员工说明、争议和处置记录；仅授权角色可见。
7. `合同履历`：沿用现有员工合同接口和查看合同入口。
8. `薪资记录`：保留现有薪资历史和编辑能力。
9. `资料与表单`：基础资料、工资卡、入职登记表、下户总结。
10. `匹配记录`：展示客户需求匹配历史、人工调整和最终结果，V1.1 启用。

页面必须做到：

- 画像结论可以下钻到观察项和原始证据。
- 风险线索与已确认风险使用不同状态和措辞。
- 没有画像数据时显示“尚无足够工作表现数据”，不得显示固定满分。
- 合同、薪资、表单等现有功能完整保留。
- 页面中不展示内部 Dify 提示词、模型参数或面向用户的操作说明文字。

#### 7.0.3 Tailwind CSS 实现约束

1. 员工管理相关新页面和重构区域统一使用 Tailwind CSS，不新增 MUI 页面组件。
2. 现有应用其他页面可继续使用 MUI，本期不进行全站 UI 框架迁移。
3. 使用现有 `lucide-react` 图标，不新增手绘 SVG 图标。
4. 弹窗、菜单、下拉、标签页等交互可复用项目现有 Radix 基础组件，样式使用 Tailwind。
5. 卡片圆角不超过 8px，不在卡片内部继续嵌套装饰性卡片。
6. 桌面端以高效信息扫描为主；窄屏下允许工具栏换行，并将表格转换为可读列表或启用合理横向滚动。
7. 固定工具栏、状态徽标、分页和操作按钮尺寸，加载或状态变化不能造成明显布局跳动。
8. 必须覆盖加载、空数据、部分接口失败、无权限、保存中、保存失败和重试状态。
9. 重构期间保持原 URL 和 API 调用兼容，避免影响从合同、考勤和动态表单跳转到员工详情的现有链路。

### 7.1 FR-01 来源记录管理

#### 7.1.1 创建来源记录

必填字段：

- 员工。
- 反馈发生时间。
- 来源类型。
- 原始转写文字或来源说明。
- 创建人。

选填字段：

- 客户。
- 合同。
- 服务阶段：面试、试工、上户初期、服务中、续签、下户、售后。
- 沟通渠道：电话、微信、当面、回访、小程序评价、投诉单、其他。
- 外部文件名、外部记录编号和备注。

业务规则：

1. 选择合同后自动带出员工和客户，不允许出现冲突绑定。
2. 未绑定合同的记录必须填写无法绑定原因。
3. 支持一条对话涉及多名员工，但必须拆分为各自独立观察项。
4. 原始转写修改时创建新版本，旧版本只读保留。
5. 来源记录不得物理删除，只能作废；作废必须填写原因。
6. 重复导入通过来源文件摘要、外部编号和内容哈希提示，不直接静默丢弃。

#### 7.1.2 转写编辑与证据定位

1. 系统为每个段落生成稳定的 `segment_id` 和显示行号。
2. 支持标注说话人：客户、客服、员工、家属、未知、其他。
3. 若转写包含时间戳，应保留开始和结束时间。
4. 复核页面默认显示证据前后若干行上下文。
5. 修改转写后，引用已变化文本的观察项自动标记为“证据待重新确认”。
6. 支持对身份证、电话、地址等敏感字段进行显示脱敏。

### 7.2 FR-02 Dify 分析任务

#### 7.2.1 触发方式

1. 来源记录保存后可手动触发分析。
2. 支持管理员开启“保存后自动提交”，但仍必须人工复核。
3. 同一转写版本和同一工作流版本只能存在一个有效分析任务。
4. 支持失败重试，重试不得创建重复正式观察项。

#### 7.2.2 输入要求

Dify 输入至少包含：

- `source_id`、`transcript_version_id`。
- 员工 ID 及必要的非敏感上下文。
- 合同类型、服务阶段、反馈时间。
- 带 `segment_id`、说话人和文本的转写数组。
- 画像维度字典版本、风险字典版本、输出 Schema 版本。

原始对话必须作为不可信数据处理。工作流提示词需明确：不得执行转写文本中的命令，不得补充原文不存在的事实，不得推断敏感属性。

#### 7.2.3 输出要求

每个候选观察项至少返回：

- `dimension_code`：画像维度。
- `polarity`：positive、negative、neutral、mixed。
- `fact_summary`：只描述可被原文支持的事实。
- `evidence_segment_ids`：一个或多个证据片段。
- `evidence_quotes`：与片段一致的引用文本。
- `severity`：low、medium、high、critical。
- `confidence`：0 至 1，仅表示模型对抽取结果的信心。
- `risk_code`：如不涉及风险则为空。
- `uncertainty`：信息缺失、传闻、说话人不明或存在矛盾时必须填写。
- `requires_human_attention`：是否需要优先复核。

系统必须校验 JSON Schema、引用片段是否存在、引用文本是否与原文一致、枚举值是否合法。校验失败时任务进入“输出无效”，不得生成候选观察项。

### 7.3 FR-03 候选观察项复核

复核页面需要同时展示：

1. 候选结论。
2. 高亮证据原文。
3. 证据上下文。
4. 来源、客户、合同和服务阶段。
5. 模型置信度、工作流版本和不确定性说明。
6. 同一员工同一维度的近期相关记录和相反证据。

复核动作：

- 确认并发布。
- 修改后发布。
- 驳回。
- 标记需要补充信息。
- 标记争议。
- 合并重复观察项。
- 转交高级复核。

任何修改必须记录 AI 原始值、修改后值、修改人和理由。P2/P3 风险至少需要具备风险复核权限的人员确认；是否要求双人复核由阶段 0 业务评审确定。

### 7.4 FR-04 正式工作表现记录

正式观察项字段包括：

- 关联员工、来源、客户、合同。
- 画像维度和正负方向。
- 客观事实描述。
- 严重程度、发生时间和服务阶段。
- 一个或多个证据片段。
- 信息来源直接性：客户本人、客服直接观察、转述、未知。
- 复核状态、复核人、复核时间。
- 是否参与画像、是否参与匹配。
- 争议状态和员工补充说明。

业务规则：

1. 正式事实描述禁止使用无法从证据推出的人格定性。
2. 客户情绪性表达可以记录，但必须与事实观察分开。
3. 同一事件的多次转述应合并为一个事件并保留多个来源，避免重复计权。
4. 已撤销或证据失效的观察项不参与画像和匹配，但保留历史审计。
5. 人工直接创建的观察项也必须绑定证据或填写“无原文证据”的明确原因，且默认不能进入高风险结论。

### 7.5 FR-05 员工画像

#### 7.5.1 画像内容

员工详情页新增“工作表现与画像”区域，包含：

- 画像更新时间和当前版本。
- 正向优势摘要。
- 需要改进摘要。
- 核心风险与待核实线索，分区展示。
- 各画像维度的证据数量、趋势和最近发生时间。
- 观察项时间线。
- 来源分布：客户数、合同数、直接反馈数、转述数。
- 数据充分度提示。

#### 7.5.2 画像生成规则

1. 只使用状态有效且允许参与画像的正式观察项。
2. 同一事件被多次转述时只计算一次，独立来源可提高证据充分度。
3. 最近表现可以拥有更高展示权重，但重大已确认风险不得因时间衰减自动消失。
4. 正面和负面证据分别统计，不允许简单相互抵消。
5. 存在相反证据时展示“表现存在波动”或“证据不一致”，不得强行输出单一结论。
6. 样本不足时显示“数据不足”，不得使用默认满分。
7. 每次观察项发布、撤销、争议状态变化或聚合规则变更时生成新画像版本。

#### 7.5.3 数据充分度

画像维度需展示以下信息，而非只显示分数：

- 有效观察项数量。
- 独立客户数量。
- 独立合同数量。
- 时间跨度。
- 最近记录日期。
- 直接证据占比。
- 是否存在争议或相反证据。

首期不建议对员工展示或业务使用单一“综合人格分”。如确需综合指标，应在业务评审后单独立项并完成公平性验证。

### 7.6 FR-06 风险管理

#### 7.6.1 风险分类

建议初始分类：

| 风险域 | 示例范围 |
| --- | --- |
| 诚信 | 对重要事实隐瞒、前后说法明显矛盾、伪造记录等线索 |
| 服务态度 | 侮辱、威胁、严重对抗、持续拒绝基本沟通等 |
| 人身安全 | 粗暴照护、危险操作、擅自用药、紧急情况处置不当等 |
| 财物安全 | 财物损坏、未经允许使用或拿取财物等线索 |
| 隐私保密 | 泄露客户家庭、健康、财务或影像信息等 |
| 责任与履约 | 无故离岗、严重迟到、擅自改变关键安排等 |
| 法律与合规 | 涉嫌违法、违规经营、骚扰、歧视等线索 |

“示例范围”仅用于分类，不表示出现关键词即可认定风险成立。

#### 7.6.2 风险等级

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 普通改进项，无明显安全或法律影响 | 纳入表现趋势 |
| P1 | 可能影响体验，需要持续观察 | 一般复核，可在匹配中提示 |
| P2 | 可能影响人身、财物、隐私或造成重大客诉 | 高级复核，限制自动推荐，记录处置 |
| P3 | 存在紧急人身安全或重大法律风险线索 | 立即通知负责人，启动人工事件流程 |

#### 7.6.3 风险处置

1. P2/P3 的系统通知只能表示“需要紧急人工调查”，不能表示事实已经成立。
2. 处置状态包括：待复核、调查中、已确认、部分确认、无法确认、已排除、已关闭。
3. 保存调查记录、员工说明、客户补充、负责人结论和后续措施。
4. 只有“已确认”或业务规则明确允许的“部分确认”风险可作为匹配强提示。
5. “待复核”和“无法确认”必须以不确定性措辞展示，不得作为自动淘汰条件。
6. 所有员工管理措施必须在系统外或独立授权流程中由人作出并留痕。

### 7.7 FR-07 客户需求管理

客户需求至少包括：

- 合同类型、服务时间、地点、预算和档期。
- 必需证书、服务经验、技能要求。
- 家庭成员和服务对象的非敏感业务信息。
- 工作内容及优先级。
- 沟通方式、生活习惯和服务偏好。
- 客户重点关注事项。
- 明确不可接受的服务冲突。

每次发起匹配必须生成需求快照，后续修改产生新版本。匹配结果始终引用当时的快照，便于复盘。

不得将客户提出的歧视性条件直接作为系统过滤或排序规则。此类内容应提示业务人员纠正或转化为合法、与工作直接相关的要求。

### 7.8 FR-08 员工匹配

#### 7.8.1 匹配分层

第一层为硬条件过滤：

- 在职和可服务状态。
- 服务日期与档期。
- 合同类型。
- 地点和可接受服务范围。
- 必需证书或技能。
- 预算和级别。

第二层为能力与偏好适配：

- 与客户重点需求对应的正向画像证据。
- 相似服务场景经验。
- 沟通、责任、卫生、专业技能等业务相关维度。
- 数据充分度和信息新鲜度。

第三层为冲突与风险提示：

- 已确认风险是否与客户重点关注事项直接冲突。
- 是否存在未完成复核的重大线索。
- 是否存在数据不足、长时间无记录或明显相反证据。

#### 7.8.2 匹配结果

每名候选员工展示：

- 硬条件通过/不通过项。
- 推荐理由，最多突出 3 至 5 项。
- 需要确认的冲突点。
- 风险提示及其状态。
- 数据充分度。
- 相关证据摘要及查看入口。
- 规则版本和画像版本。

业务人员可以调整排序、选择或排除员工，但必须记录原因。系统不得只返回一个无法解释的总分。

### 7.9 FR-09 员工说明、争议和更正

1. 授权人员可以为观察项发起员工说明流程。
2. 员工说明作为独立材料保存，不得覆盖客户原始反馈。
3. 复核人可以维持、修改、撤销或标记无法确认。
4. 争议期间，相关结论在画像和匹配中显示争议状态。
5. 错绑员工、客户或合同属于高优先级数据错误，修复后自动重算相关画像。
6. 所有更正保留修改前后版本和理由。

### 7.10 FR-10 通知和待办

系统提供以下待办：

- 待补充员工/客户/合同绑定。
- AI 分析失败或输出无效。
- 待复核候选观察项。
- 证据因转写变更而待重新确认。
- P2/P3 风险待处理或即将超时。
- 员工争议或补充说明待处理。
- 画像长时间未更新或数据不足。

通知渠道首期使用站内待办；企业微信通知仅用于 P2/P3 和超时提醒，并复用现有通知能力。

### 7.11 FR-11 搜索、筛选和导出

支持按员工、客户、合同、时间、服务阶段、维度、正负方向、风险等级、复核状态、争议状态和创建人筛选。

导出要求：

1. 默认导出画像摘要，不包含完整客户身份和原始对话。
2. 导出证据原文需要独立权限、用途说明和审计记录。
3. 导出文件包含生成时间、操作者、筛选条件和水印标识。

## 8. 状态设计

### 8.1 来源记录状态

`draft -> ready_for_analysis -> analyzing -> awaiting_review -> partially_reviewed -> completed`

异常分支：`analysis_failed`、`invalid_output`、`voided`。

### 8.2 观察项状态

`candidate -> awaiting_review -> confirmed / rejected / needs_information / disputed`

正式观察项后续可进入：`confirmed -> evidence_stale / disputed / revoked`。

### 8.3 风险状态

`flagged -> under_review -> investigating -> confirmed / partially_confirmed / unsubstantiated / dismissed -> closed`

### 8.4 分析任务状态

`pending -> running -> succeeded / invalid_output / failed / cancelled`

## 9. 初始画像维度字典

| 维度 | 主要观察内容 |
| --- | --- |
| 专业技能 | 照护、家务、月子、育儿等岗位相关能力 |
| 责任心 | 对约定任务、异常情况和结果的负责程度 |
| 服务态度 | 尊重、耐心、合作意愿、服务边界 |
| 沟通反馈 | 信息同步、倾听、解释、主动反馈 |
| 诚信 | 对关键事实、记录、承诺和错误的如实程度 |
| 守时与履约 | 到岗、请假、离岗、任务承诺执行 |
| 卫生与规范 | 环境、个人卫生和操作规范 |
| 安全意识 | 婴幼儿、产妇、老人、药物和居家安全 |
| 情绪稳定 | 面对压力、冲突和突发情况的行为表现 |
| 学习改进 | 接受反馈、纠正问题、学习新要求 |
| 家庭适配 | 与具体家庭工作方式的适配情况，不等同于人格好坏 |

维度字典必须版本化；新增、合并或废弃维度时保留历史映射。

## 10. 数据模型建议

### 10.1 `performance_sources`

保存来源记录：员工 ID、外部客户 ID、外部合同 ID、来源类型、发生时间、服务阶段、渠道、创建人、状态、内容哈希和敏感级别。

### 10.2 `performance_transcript_versions`

保存转写版本：来源 ID、版本号、原始文本、结构化分段、创建人、创建时间、变更说明和内容哈希。

### 10.3 `performance_evidence_segments`

保存稳定证据片段：转写版本 ID、片段 ID、顺序、说话人、开始/结束时间和文本。

### 10.4 `performance_analysis_jobs`

保存 Dify 任务：来源版本、工作流标识和版本、请求 ID、输入摘要、原始输出、解析输出、状态、错误、耗时、重试次数和幂等键。

### 10.5 `performance_observations`

保存候选及正式观察项：员工 ID、维度、方向、事实描述、严重程度、风险代码、来源直接性、状态、复核信息、是否参与画像/匹配和争议状态。

### 10.6 `performance_observation_evidences`

保存观察项与一个或多个证据片段之间的关系，并保留引用文本快照。

### 10.7 `employee_risk_alerts`

保存风险线索和处置：风险域、等级、状态、负责人、截止时间、调查结论、处置摘要和关联观察项。

### 10.8 `employee_profile_versions`

保存画像版本：员工 ID、版本号、生成原因、聚合规则版本、画像摘要、数据充分度、发布人和发布时间。

### 10.9 `employee_profile_traits`

保存每个画像版本的维度结果：正负证据统计、独立来源数、趋势、最近日期、充分度、摘要和相关观察项。

### 10.10 `customer_requirement_snapshots`

保存客户需求不可变快照，并关联外部客户和潜在合同/商机 ID。

### 10.11 `employee_match_runs` 与 `employee_match_results`

保存匹配运行、规则版本、候选员工、硬条件结果、适配项、冲突项、解释、人工调整和最终结果。

### 10.12 `employee_profile_audit_logs`

保存查看敏感证据、导出、复核、发布、撤销、风险处置和匹配人工调整等操作。

## 11. 主系统模块与数据归属

1. 本项目所有实际业务功能只在 ExamDB 主系统中实现。
2. 员工基础档案继续使用主系统 `ServicePersonnel`，不复制员工主数据。
3. 工作表现、证据、画像、风险和匹配相关新表建立在主系统数据库中。
4. 新表直接通过稳定 UUID 关联主系统的 `service_personnel`、`customer` 和 `contracts`。
5. 客户需求由主系统保存结构化数据及匹配快照；具体归入客户模块还是员工匹配模块在技术设计阶段确定，但仍位于主系统内。
6. 合同、档期和服务周期沿用主系统现有合同模型和业务规则。
7. 身份关联必须以稳定 UUID 为主，不以手机号、姓名等可变字段作为唯一关联依据。
8. `microservices/employee_management` 演示版本不修改、不读写、不调用，也不参与部署和验收。

## 13. Dify 对接协议

### 13.1 调用方式

1. 后端服务端调用 Dify，不允许前端持有 Dify API Key。
2. 使用异步任务执行，设置连接和总超时。
3. 保存 Dify `workflow_run_id`、请求 ID 和工作流版本。
4. 对网络错误、限流和服务端错误使用有限次数重试及退避。
5. 日志中不得明文输出 API Key 和完整敏感转写。

### 13.2 版本控制

以下内容分别版本化：

- Dify 工作流。
- 系统提示词。
- 画像维度字典。
- 风险分类字典。
- 输出 JSON Schema。
- 画像聚合规则。
- 匹配规则。

### 13.3 降级策略

1. Dify 不可用时仍允许人工录入和人工创建观察项。
2. 分析失败不得影响来源记录保存。
3. 旧画像继续可用，但明确显示最近更新时间。
4. 匹配可降级为硬条件筛选，并提示画像服务暂不可用。

## 14. 页面与交互需求

### 14.1 员工详情页

新增以下页签或区域：

- 画像总览。
- 工作表现时间线。
- 风险与待核实事项。
- 来源记录。
- 画像版本。
- 匹配记录。

“综合评分”在没有真实聚合数据时必须显示“数据不足”，不得展示固定默认值。

员工详情不是另建独立页面；上述能力必须合并进现有 `/staff/:employeeId`，并保留基础资料编辑、工资卡、薪资、合同、入职表和下户总结等已有功能。

### 14.1.1 员工管理列表页

现有 `/staff-management` 使用 Tailwind CSS 重构为紧凑运营工作台。顶部单行或可换行工具栏容纳搜索、状态筛选、画像/风险筛选和刷新；主体优先使用可排序表格；行点击进入详情，行尾保留不触发行跳转的快捷操作菜单。

页面不使用营销型大标题或装饰性统计卡。需要展示统计时使用紧凑状态条或列表标题旁计数，保证客服和运营能够快速搜索、比较和处理待办。

### 14.2 来源记录创建页

采用左右布局或分步流程：左侧绑定员工/客户/合同及上下文，右侧粘贴转写和预览分段。保存前提示敏感信息和授权要求。

### 14.3 AI 复核工作台

采用队列式工作台：左侧待复核列表，中间原文与高亮证据，右侧候选结论和复核操作。切换观察项不能丢失未保存修改。

### 14.4 风险处理页

显示事件时间线、证据、调查材料、员工说明、负责人、截止时间和处置记录。P3 使用醒目标识，但不得使用“已违法”等未经确认的文案。

### 14.5 客户匹配页

页面首先展示客户需求摘要，其次展示候选员工对比。支持按硬条件、适配项、风险冲突和数据充分度进行横向比较。

## 15. 权限、隐私与合规要求

1. 原始对话可能包含客户家庭、健康、财务和未成年人信息，应按高敏感业务数据处理。
2. 采用最小权限、按职责授权和敏感操作二次确认。
3. 页面默认脱敏客户电话、身份证、地址和其他无关信息。
4. 对原文查看、导出、风险发布和画像撤销记录审计。
5. 明确数据收集目的、授权基础、保存期限和删除/匿名化策略，并由业务及法务确认。
6. 模型不得推断健康状况、民族、宗教、性取向、政治观点等敏感属性。
7. 匹配不得以受保护属性或其明显代理变量进行负面排序。
8. 员工应有合理的说明、更正和申诉通道。
9. 画像不得作为唯一依据作出对员工有重大影响的决定。
10. 非生产环境不得直接复制真实完整转写；测试数据应脱敏或合成。

## 16. 非功能需求

### 16.1 性能

- 员工画像页面首屏接口 P95 不高于 1.5 秒，不含外部服务不可控耗时。
- 普通列表查询 P95 不高于 1 秒。
- Dify 分析采用异步方式，不阻塞页面保存。
- 单次转写长度上限和分片规则在技术评审中确定。

### 16.2 可靠性

- 来源记录和转写版本保存不得依赖 Dify 可用性。
- 分析任务具备幂等、重试、超时和死信处理能力。
- 画像重算失败时保留上一有效版本。
- 外部客户/合同服务不可用时显示明确降级状态。

### 16.3 可观测性

监控分析成功率、Schema 校验失败率、平均耗时、队列积压、复核时长、P2/P3 超时数、画像重算失败和匹配服务错误。

### 16.4 安全

- Dify API Key 加密存储并定期轮换。
- 防止提示词注入、越权访问、批量遍历和未授权导出。
- 限制转写中的恶意文件、脚本和超长输入。
- 所有接口进行参数校验、对象级权限校验和审计。

## 17. 数据分析与质量评估

灰度阶段建立人工标注样本，评估：

- 观察项抽取准确率和召回率。
- 证据引用正确率。
- 维度分类准确率。
- 风险误报率和漏报率。
- 不同复核人之间的一致性。
- 正面与负面观察项分布是否异常失衡。
- 不同员工群体是否存在无法由业务事实解释的系统性差异。
- 匹配建议被人工采用、调整和拒绝的原因。

模型指标不得替代实际业务调查，也不能仅以“人工接受率高”证明结果公平或正确。

## 18. 验收标准

### 18.1 来源和证据

- [ ] 可以创建、编辑版本和作废来源记录。
- [ ] 合同绑定后员工和客户关系校验正确。
- [ ] 转写分段具有稳定 ID、说话人、行号和可选时间戳。
- [ ] 原始转写修改后旧版本仍可查看。
- [ ] 证据失效时相关观察项自动进入待确认状态。

### 18.2 AI 和复核

- [ ] Dify 失败不影响来源记录保存。
- [ ] 输出不符合 Schema 时不会生成可发布观察项。
- [ ] AI 候选项未经人工确认不能进入画像或匹配。
- [ ] 复核人可以确认、修改、驳回、争议和转交。
- [ ] 任意修改均保留前后值和理由。

### 18.3 画像和风险

- [ ] 任意画像结论可在两次点击内定位至原始证据。
- [ ] 画像显示证据数、独立客户数、最近日期和数据充分度。
- [ ] 无有效数据时显示“数据不足”而非默认分数。
- [ ] 正面、负面、争议和相反证据分别可见。
- [ ] P2/P3 不能仅由模型自动确认。
- [ ] 风险调查和处置过程完整留痕。

### 18.4 匹配

- [ ] 匹配先执行硬条件过滤。
- [ ] 每名候选员工都有推荐理由、冲突项和数据不足提示。
- [ ] 匹配引用明确的需求快照、画像版本和规则版本。
- [ ] 人工调整排序或排除员工需要记录原因。
- [ ] 待核实风险不会被展示为已确认事实。

### 18.5 权限和审计

- [ ] 不同角色只能访问授权范围内的数据和操作。
- [ ] 查看完整原文、导出、发布风险和撤销画像均有审计记录。
- [ ] 导出执行脱敏、水印和用途记录。
- [ ] 员工说明、更正和争议处理可追踪。

## 19. 依赖

1. 员工稳定身份 ID 和员工档案接口。
2. 合同系统的合同、员工、客户和档期查询接口。
3. 客户系统的客户需求或商机数据接口。
4. 统一认证和细粒度权限能力。
5. Dify 工作流地址、API Key、网络连通性和版本管理方式。
6. 异步任务、队列或等价后台任务执行能力。
7. 企业微信或站内待办通知能力。
8. 对象存储或受控文件存储，用于来源附件和导入文件。

## 20. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 转写错误或说话人识别错误 | 结论引用错误 | 人工确认说话人、保留上下文、允许更正 |
| 单次投诉被过度放大 | 员工受到不公平影响 | 独立来源统计、数据充分度、争议和人工复核 |
| AI 幻觉或错误分类 | 产生错误画像 | 强制证据 ID、Schema 校验、禁止自动发布 |
| 重复转述被重复计权 | 风险被夸大 | 事件归并和来源去重 |
| 敏感对话泄露 | 隐私和合规风险 | 最小权限、脱敏、审计、限制导出和留存 |
| 历史记录身份映射不准确 | 错绑员工或合同 | 统一 UUID、映射校验、禁止手机号或姓名作为主关联键 |
| 匹配规则形成偏见 | 不公平排序 | 仅使用工作相关条件、人工复核和群体差异监控 |
| Dify 服务不稳定 | 分析积压 | 异步重试、降级人工处理、积压监控 |

## 21. 待业务确认事项

1. 哪些角色可以确认 P0/P1，哪些角色可以确认 P2/P3？
2. P2/P3 是否强制双人复核，以及响应时限分别是多少？
3. 员工可查看的结论范围、申诉入口和处理时限是什么？
4. 原始转写和附件的法定或业务保存期限是多少？
5. 客户是否已就录音、转写和分析取得适当授权？
6. 客户需求目前存储在哪个系统，是否已有结构化字段？
7. 首期匹配范围是月嫂、育儿嫂，还是覆盖所有服务人员？
8. 风险成立后的业务措施是否已有独立制度和审批流程？
9. Dify 工作流由谁维护，如何进行版本发布和回滚？
